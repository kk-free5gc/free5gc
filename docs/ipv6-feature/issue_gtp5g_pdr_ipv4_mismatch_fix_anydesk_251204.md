# GTP5G PDR IPv4 Mismatch Caused by PC Dual-Homing (Anydesk Traffic)

**Date:** December 4, 2025  
**Issue:** UL packets on TEID 0x2 intermittently fail `pdr_find_by_gtp1u()` with an IPv4 UE mismatch  
**Component:** `gtp5g` kernel module / UE PC routing  
**Status:** ✅ Mitigated (root cause outside UPF)

---

## Error logs (dmesg)

```
[Wed Dec  3 08:03:05 2025] [gtp5g] wnc_log_pdr_mismatch: WNC: PDR[1] TEID[0x2] mismatch: IPv4 UE address mismatch | af=0x2 v4=1 v6=0 inner=v4
[Wed Dec  3 08:03:05 2025] [gtp5g] wnc_log_pdr_mismatch: WNC:   Inner IPv4: 169.150.222.205 -> 192.168.6.10
[Wed Dec  3 08:03:05 2025] upfgtp:[gtp5g] gtp1u_udp_encap_recv: No PDR match this skb : teid[2]
```

## Issue Summary

- Kernel log spam: `gtp1u_udp_encap_recv: No PDR match this skb : teid[2]` around 08:02:55–08:03:13 UTC.  
- New instrumentation (`wnc_log_pdr_mismatch()`) showed repeated drops because the inner IPv4 source **did not** equal the provisioned UE IPv4 (`10.155.0.1`).  
- Captured packets (`test-21-n3-upf.pcapng`) revealed additional flows tunneling through TEID 0x2, e.g. `10.155.0.1 → 169.150.222.205` and `169.150.222.205 → 192.168.6.10`.  
- None of these addresses were ever configured in free5GC; PDR 1 remained bound to UE IPv4 `10.155.0.1` the entire time.

## Investigation Timeline

1. **Initial instrumentation (Dec 3, ~07:43)**  
   Added helper `wnc_log_pdr_mismatch()` in `gtp5g/src/pfcp/pdr.c` to log inner IPv4/IPv6 plus AF flags whenever `pdr_find_by_gtp1u()` rejects a packet.

2. **Test run 20 (`dmesg-20.log` / `free5gc-20.log`)**  
   Logs show `Inner IPv4: 169.150.222.205 -> 192.168.6.10` on TEID `0x4` exactly when `gtp1u_udp_encap_recv` drops packets.  
   Confirmed the PDR still stored UE IPv4 `10.155.0.1`; no PFCP updates removed it.  
   Hypothesis: foreign traffic entering the UL tunnel from the UE/gNB side.

3. **Extended capture + log level (Test run 21)**  
   `test-21-n3-upf.pcapng` captured both `br-ng` (interface_id=0) and `upfgtp` (interface_id=1).  
   Quick parser summary (TEID 0x2):
   - `10.155.0.1 → 8.8.8.8`: 74 packets (expected)  
   - `10.155.0.1 → 220.128.8.77`: 39 packets  
   - `10.155.0.1 → 169.150.222.205`: 21 packets  
   - `169.150.222.205 → 192.168.6.10`: 10 packets

4. **Configuration review**  
   UE PC has two active interfaces: `10.155.0.1` (5G) and `192.168.6.10` (LAN/SSH).  
   Default route preferred the 5G interface; AnyDesk traffic to servers such as `169.150.222.205`, `185.125.190.98`, etc. therefore egressed the PDU session.  
   When AnyDesk bridged to the LAN, even `169.150.222.205 → 192.168.6.10` responses traversed TEID 0x2, triggering the mismatch instrumentation.

## Root Cause

UE-side routing allowed non-UE addresses (AnyDesk remote-control flows) to be transported over the 5G tunnel. The UPF correctly enforces that the inner source address of an uplink packet matches the configured UE IPv4. Every packet sourced from `169.150.222.205` or destined for the PC's LAN interface therefore failed the PDR lookup and was dropped.

### Anydesk Identification Evidence

The reason for suspecting **"Anydesk"** as the application causing this issue is based on the following evidence found in payload analysis of packets between `10.155.0.1 <-> 169.150.222.205`:

- **Keywords found in packet payloads:**
  - `"anynet"`
  - `"anydesk"`
  - `"philandro software GmbH"` (Anydesk's developer company)

### Future Verification Method

For future troubleshooting of similar issues, verify if an IP address (e.g., `169.150.222.205`) is actually an Anydesk server by running the following commands on the UE PC:

```bash
# Check active Anydesk connections with socket statistics
ss -ntp | grep anydesk

# Alternative: Use netstat to find Anydesk connections
netstat -ntp | grep anydesk
```

**Reference trace file:** `/home/wnc/anydesk.trace`

## Resolution & Mitigation

1. **Validated capture evidence**  
   Confirmed via packet parsing that these flows existed on N3/UPF interfaces; they were not generated by the UPF.  
   Downlink TEID `0x0c00010c` simultaneously carried the reverse traffic from the same AnyDesk servers.

2. **Adjusted UE routing**  
   Lowered the priority of the 5G default route so the PC now prefers its LAN (`192.168.6.0/24`) for AnyDesk and other remote-control traffic.  
   After the change, `wnc_log_pdr_mismatch` no longer reports the 169.150.222.205 tuples, and the drop spam stopped.

3. **Documentation**  
   Captured this analysis for future reference in case similar “foreign IP” drops reappear.

## Remaining Observations

- `gtp1u_udp_encap_recv: No PDR match this skb : teid[X]` still occurs occasionally due to other expected events (e.g., gNB release), but no longer follows the AnyDesk signature.  
- If future requirements demand tunneling arbitrary LAN traffic, SMF/UPF must install additional PDRs covering those addresses; otherwise the UE must ensure only its allocated IP traverses the bearer.
