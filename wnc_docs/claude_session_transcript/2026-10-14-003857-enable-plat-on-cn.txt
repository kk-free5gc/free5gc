  ★ Insight ─────────────────────────────────────
  - In this lab the UPF is not a separate box. config/upfcfg.yaml shows that the
    UPF runs on the cn host itself, with N3 address 5.5.5.2 and the gtp5g
    kernel module as the forwarder. The gtp5g module removes the GTP-U header
    from each uplink packet and hands the inner IPv6 packet to the cn kernel on
    the upfgtp interface. NAT64 (the IPv6-to-IPv4 translator, called the PLAT on
    the core side) can therefore run on cn itself. Step 2 of the pasted text
    ("route 64:ff9b::/96 to a separate host") is then not needed.
  - Jool in --netfilter mode hooks the kernel's netfilter PREROUTING stage. It
    catches any IPv6 packet addressed to 64:ff9b::/96, including packets that
    arrive from upfgtp, before the kernel makes a routing decision. Jool also
    catches the IPv4 replies that come back to the cn IPv4 address and turns
    them back into IPv6. The kernel then routes those IPv6 replies to the UE
    prefix through upfgtp, which is the downlink route that already works for
    slice 122.
  - The free5gc UPF Router Advertisement (RA) code has no PREF64 option. PREF64
    (RFC 8781) is an RA option that tells the UE the NAT64 prefix directly.
    Without PREF64, the UE learns the prefix in one of two ways: you set it by
    hand (the ip6prefix option on the UE side), or the UE runs DNS64 discovery.
    In DNS64 discovery the UE asks DNS for the AAAA record of ipv4only.arpa
    (RFC 7050).

  Plan for the cn host

  None of these commands has been run on cn yet. Run them in this order.

  Step 1: Install Jool and start the NAT64 (the PLAT)

  This step installs the Jool kernel module and its command-line tools, and
  turns on forwarding. It then starts one stateful NAT64 instance for the
  well-known prefix 64:ff9b::/96.
  sudo apt install -y jool-dkms jool-tools
  sudo sysctl -w net.ipv4.ip_forward=1
  sudo sysctl -w net.ipv6.conf.all.forwarding=1
  sudo modprobe jool
  sudo jool instance add "plat" --netfilter --pool6 64:ff9b::/96
  sudo jool -i plat instance display
  - jool-dkms compiles the Jool kernel module against the running kernel. The cn
    kernel changed after the recent reboot, so check that dkms status shows
    jool as installed for uname -r.
  - Pool4 is the set of IPv4 addresses and ports that Jool uses as the shared
    public source. When pool4 is empty, Jool uses the cn host's own IPv4 address
    on the egress interface, with ports 61001–65535. That works if cn already
    reaches the Internet over IPv4.
  - The commands above do not survive a reboot. To keep IPv6 forwarding after a
    reboot, use the same method as the persistent UPF IPv6 forwarding fix from
    the slice-122 IPv6 work.

  Step 2: Test the PLAT alone, before the UE CLAT is involved

  From the UE, on an IPv6 PDU session (slice 122 is the one already known to
  work), ping an IPv4 host through its NAT64 address:
  ping6 64:ff9b::808:808
  64:ff9b::808:808 is 8.8.8.8 written inside the NAT64 prefix. On cn, sudo jool 
  -i plat session display --icmp should then list the translation session. If
  the ping works, the PLAT works, and any later failure is on the UE CLAT side.
  (CLAT is the UE-side translator that turns IPv4 traffic into IPv6.)

  Step 3: Test the UE CLAT with a fixed prefix (no core changes)

  Use an IPv6-only PDU session. Remember that an IPv6-only session needs the
  IPv4 N3 F-TEID 5.5.5.2, as recorded in the N3 memory. Set the UE CLAT prefix
  by hand to 64:ff9b::/96 (the ip6prefix option). Then ping 8.8.8.8 from the UE,
  or from the LAN client behind it. DNS also works in this mode, because the
  CLAT carries IPv4 DNS queries to 8.8.8.8 through the NAT64.

  Step 4 (optional): DNS64 on cn, to test automatic prefix discovery

  4a. This command gives the DNS64 server an IPv6 address that the UE can reach.
  It puts a new address on the cn loopback interface. The address
  2001:db8:ffff::53 is only an example; pick any address outside the UE pools.
  sudo ip -6 addr add 2001:db8:ffff::53/128 dev lo

  4b. This step installs unbound and writes its DNS64 configuration, one echo
  line per line of the file. unbound forwards queries over IPv4 to 8.8.8.8,
  because cn has no IPv6 route to the Internet. The ip-freebind line lets
  unbound start even if the loopback address is missing.
  sudo apt install -y unbound
  echo 'server:' | sudo tee /etc/unbound/unbound.conf.d/dns64.conf
  echo '  interface: 2001:db8:ffff::53' | sudo tee -a
  /etc/unbound/unbound.conf.d/dns64.conf
  echo '  ip-freebind: yes' | sudo tee -a /etc/unbound/unbound.conf.d/dns64.conf
  echo '  access-control: 2001:db8::/32 allow' | sudo tee -a
  /etc/unbound/unbound.conf.d/dns64.conf
  echo '  module-config: "dns64 iterator"' | sudo tee -a
  /etc/unbound/unbound.conf.d/dns64.conf
  echo '  dns64-prefix: 64:ff9b::/96' | sudo tee -a
  /etc/unbound/unbound.conf.d/dns64.conf
  echo 'forward-zone:' | sudo tee -a /etc/unbound/unbound.conf.d/dns64.conf
  echo '  name: "."' | sudo tee -a /etc/unbound/unbound.conf.d/dns64.conf
  echo '  forward-addr: 8.8.8.8' | sudo tee -a
  /etc/unbound/unbound.conf.d/dns64.conf
  sudo systemctl restart unbound
  dig AAAA ipv4only.arpa @2001:db8:ffff::53
  The dig result should include 64:ff9b::c000:aa (the NAT64 form of
  192.0.0.170). unbound listens only on that one address, so it does not clash
  with systemd-resolved on 127.0.0.53.

  4c. This is the free5gc change. In config/smfcfg.yaml, change dns.ipv6 for the
  DNN under test from 2001:4860:4860::8888 to 2001:db8:ffff::53, then restart
  the SMF. After that, remove the manual ip6prefix from the UE so that the UE
  discovers the prefix itself.

  Caveats

  - RFC 6052 does not allow the well-known prefix 64:ff9b::/96 to reach private
    IPv4 addresses, and Jool follows that rule. Test against public IPv4 targets
    such as 8.8.8.8, not lab 10.x or 192.168.x hosts.
  - The current uplink rule (permit out ip from assigned to any) already allows
    any destination. No change to the SMF or UPF packet rules is needed for
    64:ff9b::/96.

● Why 64:ff9b::/96

  --pool6 tells Jool which IPv6 destination addresses to translate. Jool
  translates a packet only when its destination is inside 64:ff9b::/96. Every
  other IPv6 packet passes through cn unchanged, for example the existing
  traffic to 2001:db8:126::1.

  ★ Insight ─────────────────────────────────────
  - 64:ff9b::/96 is the Well-Known Prefix that RFC 6052 reserves for IPv4/IPv6
    translation. The /96 leaves the last 32 bits for an IPv4 address. Jool takes
    the IPv4 destination straight from those 32 bits:
    64:ff9b::808:808 → last 32 bits 0808:0808 → 8.8.8.8
    64:ff9b::c000:aa → c0.00.00.aa → 192.0.0.170
    No per-host rule or table is needed. One prefix covers the whole IPv4
    Internet.

    prefix that nobody translates:

       answers, Step 4c)

● That output explains the timeout, and the cause is on the UE, not on cn.

  The UE kernel sends traffic for 2001:db8:53::53 out of ccmni1 (via fe80::1 dev
  ccmni1), because that is the route it matches. Since ccmni1 cannot reach the
  core right now, the DNS query is lost there. ping -I ccmni2 worked only
  because -I forced the interface. BusyBox nslookup has no such option, so it
  follows the routing table.

  There is a second problem in the same line. The source address is src 
  2001:db8:131:1::2, which is ccmni2's address, yet the packet leaves through
  ccmni1. Even if ccmni1 were working, its PDU session would carry a packet
  whose source is another session's address. The UPF matches uplink packets to a
  session by the UE address. Such a packet would therefore not match the ccmni1
  session and would be dropped.

  ★ Insight ─────────────────────────────────────
  - Each ccmni interface is a separate PDU session with its own GTP-U tunnel and
    its own UE prefix. A packet only works when its source address belongs to
    the session whose interface it leaves through. Without per-interface routing
    on the UE, the default route decides, and the source address is picked
    separately. That mismatch is the same multi-PDN IPv6 routing problem seen
    earlier on slices 131/141.
  - The same rule applies to the CLAT. The CLAT sends its translated IPv6
    packets to 64:ff9b::/96, and the routing table decides which ccmni they
    leave through. ping -6 64:ff9b::808:808 worked earlier only because of -I 
    ccmni2. Without a route for 64:ff9b::/96 through ccmni2, CLAT traffic would
    take ccmni1 and fail in the same way.
    ─────────────────────────────────────────────────

  Fix for the test: two host routes on the UE through ccmni2
