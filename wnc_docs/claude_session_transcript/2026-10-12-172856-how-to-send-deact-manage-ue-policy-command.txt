  buildInstruction then always writes the part length and the type byte.

  What this probably does on the UE: the UE treats the instruction as "replace
  section 3001 with a URSP part that has no rules". The UE may keep the UPSI
  (PLMN ID + UPSC) stored, so step 4 of your VERIFY list (UPSC: 0x0bb9
  disappears) would fail. The UE may also answer with MANAGE UE POLICY COMMAND
  REJECT, because a URSP part with no rules is unusual. I have not tested this
  on the UE.

  are:

● What the fix would change

  The text you pasted and my finding say the same thing. A delete instruction
  carries the PLMN ID and the UPSC (UE Policy Section Code), and its UE policy 
  section contents must be empty. Your YAML file already asks for that, because
  it sets policyParts: []. The problem is that the free5GC encoder does not send
  what the YAML asks for. It puts something into the contents.

  Here are the bytes the encoder builds today for UPSC 3001, compared with what
  the pasted text requires:

  ┌────────────────────┬──────────────────────────────────┬────────────────┐
  │    Part of the     │         Bytes sent today         │  Bytes for a   │
  │    instruction     │                                  │  real delete   │
  ├────────────────────┼──────────────────────────────────┼────────────────┤
  │ Instruction length │ 0005                             │ 0002           │
  ├────────────────────┼──────────────────────────────────┼────────────────┤
  │ UPSC               │ 0bb9 (3001)                      │ 0bb9 (3001)    │
  ├────────────────────┼──────────────────────────────────┼────────────────┤
  │ UE policy section  │ 0001 01: one UE policy part,     │ nothing        │
  │ contents           │ length 1, type URSP, zero rules  │                │
  └────────────────────┴──────────────────────────────────┴────────────────┘

  The contents are not empty today. 0001 01 is a URSP part that holds no rules.
  The UE can read that as "replace section 3001 with an empty URSP list" rather
  than "delete section 3001". In that case the UE would keep reporting UPSC: 
  0x0bb9.

  Why the encoder adds those 3 bytes

  convertYAMLToInternalConfig creates every instruction with PolicyPart: 
  UEPolicyPartConfig{Type: 1}, even when policyParts is empty. Then
  buildInstruction always writes a part length and a type byte after the UPSC.
  The same code is in two copies:
  - NFs/amf/internal/policy/ue_policy.go:274, used by the AMF
  - NFs/pcf/internal/policy/ue_policy.go:214, used by the PCF

  The path the policy takes from your config decides which copy builds the
  message, so both copies need the same change.

  The change, in both files

  1. convertYAMLToInternalConfig: if an instruction's policyParts list is empty,
     leave PolicyPart.Type at 0 instead of setting it to 1. Type 0 is reserved
     in TS 24.501 (1 = URSP, 2 = ANDSP), so a real policy part never has type 0.
     That makes 0 safe to mean "this instruction has no policy part".
  2. buildInstruction: if PolicyPart.Type is 0, write only the 2-byte UPSC. Skip
     the part length and the type byte. The instruction length then comes out
     as 0002.
  3. A new test in each package: load pcfcfg_ue_policy_tmo_del.yaml and check
     that the output is 80 01 000d 000b 130062 0002 07d1 0002 0bb9.

  Instructions that do have policy parts are not affected. The existing test
  TestBuildManageUEPolicyCommand_TMobile checks the T-Mobile install message
  byte for byte, and it should still pass.

    pcfcfg_ue_policy_tmo_del.yaml.
