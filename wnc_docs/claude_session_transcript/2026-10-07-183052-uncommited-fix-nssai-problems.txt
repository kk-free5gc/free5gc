● What went wrong

  The AMF received Security Mode Complete and started building the Registration
  Accept. It stopped during the network slice check, decided that a different
  AMF must serve the UE, could not find one, and then sent nothing to the CU.
  The CU waited about 4.5 seconds and sent UEContextReleaseRequest.

  Root cause: the UE asks for slices that its subscription does not contain

  The Registration Request from imsi-310260000013069 carries this Requested
  NSSAI (the list of network slices the UE asks for). I decoded it from log line
  1375:

  ┌────────────────────────────────────────────────┬────────────────────────┐
  │     Requested S-NSSAI (slice type / slice      │      In the UE's       │
  │                differentiator)                 │     subscription?      │
  ├────────────────────────────────────────────────┼────────────────────────┤
  │ SST 1 / SD 050601                              │ No                     │
  ├────────────────────────────────────────────────┼────────────────────────┤

  The UDM returns four subscribed slices for this SUPI: 1/000001 (marked as
  default), 1/0007D0, 1/000BB8 and 1/000BB9. You can see them in the NSSF query
  on log line 1397.

  How the AMF reacts, step by step (NFs/amf/internal/gmm/handler.go)

  1. Line 1183: handleRequestedNssai checks the first requested slice, 1/050601.
     That slice is not in ue.SubscribedNssai, so the function sets
     needSliceSelection = true and leaves the loop with break. The function
     never looks at the remaining requested slices, so ue.AllowedNssai stays
     empty.
  2. Line 1227: The AMF asks the NSSF for slice selection. The NSSF logs No TA 
     {310/260, tac 000001} in NSSF configuration and returns 200 without any
     target AMF set.
  3. Line 1242: The AMF calls RegistrationStatusUpdate toward the "old AMF". The
     UE's old 5G-GUTI points at AMF ID 800101 in PLMN 001/01, which does not
     exist here, so the log shows Registration Status Update Error[amf not 
     found].
  4. Line 1278: The AMF asks the NRF for another AMF.
     SearchAmfCommunicationInstance (nrf_service.go:165) skips its own instance
     and finds no other AMF, so the log shows AMF can not select an target AMF 
     by NRF.
  5. Line 1322: As the last option, the AMF tries to send an NGAP
     RerouteNASRequest to the CU. The AllowedNSSAI information element in that
     message must hold at least one slice. Step 1 left the list empty, so ASN.1
     encoding fails with Build RerouteNasRequest failed : SEQUENCE OF Size is 
     lower than lowerbound.
  6. Line 1323 → line 641: handleRequestedNssai returns the error to
     HandleInitialRegistration. That function returns immediately, and the GMM
     state machine moves ContextSetup → Deregistered. No Registration Reject is 
     sent on this path. The CU therefore gets no answer at all.

  Your allowedNssaiMode: allSubscribedAlways code at lines 1331–1372 never runs
  here. The function returns at line 1323, before it reaches that code.

  All four registration attempts in this log fail the same way (log lines 1011,
  1375, 2044 and 2409). The UE sends the identical Requested NSSAI every time,
  and the log contains no Send Registration Accept at all.

  ★ Insight ─────────────────────────────────────
  - Stock free5gc treats "a requested slice is not subscribed" as a reason for
    AMF re-allocation (TS 23.502 §4.2.2.2.3). It does not simply put that slice
    into the Rejected NSSAI. In a single-AMF lab, re-allocation can never
    succeed.
  - The break at line 1196 means a single unsubscribed slice at the front of the
    list stops the check of every later slice. Here that left AllowedNssai
    empty. The same list in a different order would still trigger re-allocation,
    but the reroute message would at least encode.
  - The silent failure is a separate defect. When re-allocation is impossible,
    TS 24.501 expects the AMF to answer the UE, either with a Registration
    Accept that carries a Rejected NSSAI or with a Registration Reject. The AMF
    should not drop the procedure without a reply.
    ─────────────────────────────────────────────────

  Ways to fix it (I have not changed anything)

  - Subscriber data (no code change): In the webconsole, add 1/050601, 2/050602,
    3/050603 and 3/050503 to the subscription for imsi-310260000013069. Then
    every requested slice is subscribed, and the AMF does not try re-allocation.
    Note that 3/050503 is also missing from the AMF plmnSupportList, so you
    would need to add it there too.
  - UE side: Configure the UE so that it requests only the slices it is
    subscribed to.
  - AMF code: Change handleRequestedNssai so that it puts unsubscribed slices
    into the Rejected NSSAI and keeps the subscribed slices in the Allowed
    NSSAI. With that change, it would skip re-allocation whenever no other AMF
    exists. You could also add a SendRegistrationReject call on the
    failed-reroute path, so the CU gets a reply instead of waiting for its
    timer.

  the UE's stored context. The free5gc AMF refuses any InitialUEMessage without
  that field, except one carrying an Initial Registration. It answers with
  ErrorIndication and then releases the UE with cause Protocol=unspecified.

  The UE retries immediately, so the cycle repeats. The log has 3020 Missing 
  5G-S-TMSI IE in InitialUEMessage; send ErrorIndication warnings, about 5–6 per

● Your questions

  1. Are the "Allowed" list and the "Default" list different? Yes. They are
  different kinds of thing, and the "default" one is not really a separate list:

  Name: Subscribed S-NSSAIs
  What it is: Every slice the UE is entitled to use
  Who sets it: Operator, in the webconsole
  Stored in: MongoDB subscriptionData.provisionedData.amData → nssai, which
  holds
  2 arrays: defaultSingleNssais and singleNssais
  ────────────────────────────────────────
  Name: Default S-NSSAIs
  What it is: The Subscribed S-NSSAIs in the defaultSingleNssais array. Each one

  is marked "default" (defaultIndication)
  Who sets it: Operator (the webconsole "default" mark)
  Stored in: Same document as above
  ────────────────────────────────────────
  Name: Allowed NSSAI
  What it is: The slices the AMF lets the UE use in this registration
  Who sets it: AMF, at each registration: Requested NSSAI ∩ Subscribed S-NSSAIs
  ∩
  AMF-supported slices
  Stored in: AMF memory only (ue.AllowedNssai); sent to the UE in Registration
  Accept

  So a default S-NSSAI is a mark on a subscribed slice, and the Allowed NSSAI is
  a per-registration result. A default S-NSSAI can be in the Allowed NSSAI or
  not.

  2. Is useDefaultSnssaiForPduSession the wrong name? Yes, you are right. The
  AMF always picks from the Allowed NSSAI. The default mark only decides which 
  Allowed S-NSSAI wins. A clearer name is preferSubscribedDefaultInAllowedNssai:
  "within the Allowed NSSAI, prefer the S-NSSAI that the subscription marks as
  default".

  3. What is "subscription data", and what is "policy data"? Both live in
  MongoDB, and each is read by a different NF:

  Name in the comment: Subscription data: DNN list per slice
  MongoDB collection: subscriptionData.provisionedData.smData
  Read by: SMF (through UDM)
  What it holds for each slice: The DNNs allowed on that slice, with PDU session

  types, AMBR and 5QI
  Missing entry causes: SMF warning Subscriber data missing PDU session types 
  for
   DNN[...]
  ────────────────────────────────────────
  Name in the comment: Policy data: DNN list per slice
  MongoDB collection: policyData.ues.smData
  (smPolicySnssaiData[slice].smPolicyDnnData[dnn])
  Read by: PCF (through UDR)
  What it holds for each slice: Policy data for each slice/DNN pair
  Missing entry causes: UDR 404 → PCF error (today: the panic)

  The webconsole writes both collections when you add a DNN to an S-NSSAI on the
  subscriber page.
